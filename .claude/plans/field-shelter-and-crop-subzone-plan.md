# Plan: Split the field into a crop-area Subzone + a small work-site Building

## Context

Supersedes the field-as-`Building` design shipped in
[field-placement-plan.md](field-placement-plan.md). That design overloaded
`Building` with two different jobs: the crop-growing area (a large 35-60
unit footprint, sized to visually read as a field) and the walkable
work-site (entrance node, interior spaces, `CharacterLocation` target).
Those are genuinely different things - a crop area isn't a structure you
walk into.

This plan splits them:
- **Crop area** → a `Subzone` (`usage="crops"`), under a per-village
  `LandArea` - existing-but-unused models, generated by
  `generate_landarea.py` today but never wired into the map or anything
  else. This finally puts them to work.
- **Work-site** → a new small `Building` (a field shelter/noticeboard,
  sized like a house - 10-20 units, not 35-60), which becomes the
  `CharacterLocation`/`assign_workers`/pathing target instead of the field
  itself.

This is a prerequisite for
[wheat-harvest-simulation-plan.md](wheat-harvest-simulation-plan.md)'s
`FieldCrop` model, which will reference the Subzone for area and the
shelter Building for physical-presence checks.

---

## 1. High-level strategy

- `generate_fields.py` is rewritten: instead of creating one oversized
  `Building(building_type="field")`, it creates a `Subzone` (crop area,
  reusing the exact placement/overlap-avoidance logic already built - it's
  generic polygon math, not building-specific) plus a small `Building`
  (the shelter) sited on the crop area's edge via the existing
  `compute_building_entrance_point` helper.
- `Building.BUILDING_TYPES`'s `"field"` choice is renamed to
  `"field_shelter"` to reflect what it now actually is - a small structure,
  not the field.
- The map view gains a new `SubzoneFeatureSerializer` (mirrors
  `BuildingFeatureSerializer`) and includes `usage="crops"` subzones in its
  features/bbox. The frontend moves the gold fill from
  `building_type === "field"` to `feature_type === "subzone" &&
  properties.usage === "crops"`.
- `generate_landarea.py`'s existing (separately-scoped, centered-on-village)
  LandArea/Subzone generation is untouched - this plan creates its own
  dedicated per-village `LandArea` for farmland, independent of that
  command, to avoid coupling to its flawed placement and to avoid a pipeline
  ordering dependency (`generate_fields` runs early in `setup_world.py`;
  `generate_landarea` runs last).

  fixing while touching this rename anyway, small entry like a
  noticeboard/lean-to needs minimal interior space, e.g. mostly `"other"`
  with a small `"storage"` sliver for tools).

## 3. Implementation plan

1. Rename `Building.BUILDING_TYPES`'s `"field"` → `"field_shelter"`;
   generate the migration (schema change) + a data migration renaming
   existing rows (handles any already-seeded dev/staging data).
2. Add `SubzoneFeatureSerializer` to `locations/serializers.py`.
3. Rewrite `generate_fields.py`:
   - Keep the existing `_find_field_placement`-style retry loop
     (angle/margin around the village, avoid own boundary, avoid other
     villages' boundaries) - apply it to the crop-area polygon instead of a
     building footprint. Same constants, same idempotent per-centre skip
     (now keyed on "does this centre already have a crops `Subzone`" instead
     of "already have a field building").
   - Once a valid crop-area polygon + point is found: `get_or_create` a
     per-village `LandArea` (e.g. `f"{centre.name} Farmland"`), create the
     `Subzone(usage="crops", boundary=crop_polygon, size=area/10000)` under
     it (m² → hectares, matching `generate_landarea.py`'s existing
     convention).
   - Place the shelter `Building` at `compute_building_entrance_point(crop_polygon, candidate)`
     (reuses the existing "midpoint of the longest edge" helper - it's
     generic, not building-specific), sized via `create_building_footprint`
     with house-like min/max (reuse `spawn_villages`'s residential sizing
     constants rather than inventing new ones).
   - Node/entrance-node creation for the shelter Building is unchanged from
     today's logic (`Node.Kind.BUILDING` + `Node.Kind.BUILDING_ENTRANCE`).
4. Update `assign_workers.py`, `character/utils.py`,
   `populate_interiors.py` for the renamed building type.
5. `PopulationCentreMapView`: query `population_centre.land_areas.first().subzones.filter(usage="crops")`
   (or a direct `Subzone.objects.filter(land_area__population_centre=population_centre, usage="crops")`
   - simpler, no dependency on exactly one `LandArea`), serialize via
   `SubzoneFeatureSerializer`, append to `features`, fold extents into
   `bbox` the same way buildings already are.
6. Frontend: swap the gold-fill condition and add the `field_shelter` label;
   update the Map test fixture/assertions.
7. Rewrite `GenerateFieldsCommandTest` for the new shape (crop Subzone +
   shelter Building, both avoiding the village's own boundary and other
   villages').

## 4. Design decisions

**Dedicated per-village `LandArea` vs. reusing `generate_landarea.py`'s
output.** Chosen: `generate_fields.py` creates and owns its own `LandArea`
("Farmland"), independent of whatever `generate_landarea.py` produces.
Alternative: make `generate_fields` depend on `generate_landarea` having
already run, and attach the crops `Subzone` to that existing `LandArea` -
rejected: `generate_landarea` runs *after* `generate_fields` in
`setup_world.py`'s pipeline (fields must exist before `generate_paths`,
landarea generation is decorative/last), and its placement is centered on
the village rather than offset outward like fields need. Reordering the
whole pipeline or fixing `generate_landarea`'s placement logic is a larger,
separate piece of work than this plan needs to take on.

**Rename `"field"` → `"field_shelter"` vs. keep the choice name and just
change what it represents.** Chosen: rename. Leaving the DB value as
`"field"` while it now means "a small shelter building, not the field
itself" is exactly the kind of naming drift that causes confusion later
(e.g. a future engineer assuming `building_type="field"` buildings are
large). Alternative: keep `"field"` and rely on comments - rejected, the
rename is a single migration and touches a small, contained set of call
sites (all found and listed above).

**Subzone lookup via `land_area__population_centre` filter vs. via
`population_centre.land_areas.first()`.** Chosen: direct filter - a
population centre could in principle have more than one `LandArea` (e.g. if
`generate_landarea.py` is later run too), and `.first()` on an unordered
relation is fragile. A direct `Subzone.objects.filter(land_area__population_centre=pc, usage="crops")`
is unambiguous regardless of how many `LandArea` rows exist.

## 5. Edge cases

- **Existing seeded worlds with `"field"` buildings.** The data migration
  renames them to `"field_shelter"`, but they'll still have oversized
  footprints and no associated crop `Subzone` - acceptable for dev/staging
  (reseed via `setup_world`/`seed_village_view` after migrating), not
  something the migration itself needs to reconcile geometrically.
- **Crop `Subzone` avoiding the village's own boundary and other villages'
  boundaries** - identical retry-loop logic to the current field placement,
  just checked against the crop polygon instead of a building footprint;
  same `PLACEMENT_ATTEMPTS` exhaustion warning-and-skip behaviour.
- **Shelter Building placement point lands exactly on the crop `Subzone`'s
  boundary edge (by construction, via `compute_building_entrance_point`).**
  This overlap is intentional (the shelter should touch its field) and is a
  different case from the boundary-fusion problem fixed earlier - it's the
  crop area's edge, not the village boundary.
- **Idempotency** - re-running `generate_fields` should skip a centre that
  already has a crops `Subzone` for its `LandArea`, mirroring the current
  "already has a field" skip.

---

## 6. Tests

- Crop `Subzone` is created with `usage="crops"`, avoids the centre's own
  boundary and other centres' boundaries (port the three existing
  `GenerateFieldsCommandTest` cases to the new shape).
- Shelter `Building` is created with `building_type="field_shelter"`, has
  entrance + central nodes, and its footprint size is house-scale (smaller
  than the crop area).
- Re-running the command is a no-op for a centre that already has a crops
  `Subzone`.
- Map view: a population centre with a crops `Subzone` includes a `subzone`
  feature in its response, and the response `bbox` covers it even when it
  sits outside the boundary polygon.
- Frontend: crops-usage subzone feature renders gold; a `field_shelter`
  building renders in the default grey (not gold) - update/replace the
  existing "renders field buildings in gold" test.

---

## 7. Risks

- Missing a `"field"` reference during the rename (e.g. in
  `character/utils.py`'s `WORK_ACTIVITIES_BY_BUILDING_TYPE` or
  `populate_interiors.py`) silently falls back to `"default"`/`"other"`
  rather than erroring - worth a repo-wide grep for `"field"` (not just
  `building_type="field"`) before considering the rename complete, since
  it's a common English word and easy to miss a usage.
- Forgetting to fold subzone extents into the map view's `bbox` reintroduces
  the exact "field disappears off the edge" clipping bug already fixed once
  for buildings.
- `compute_building_entrance_point` picks the *longest* edge of the crop
  polygon, not necessarily the edge facing the village - for a roughly
  square crop area this can place the shelter on the wrong side, producing
  a slightly longer path than necessary. Cosmetic, not a correctness bug;
  not worth solving in this pass.

---

## 8. Open questions

- Should the crop `Subzone`'s size (hectares) be tuned independently from
  the old field-footprint sizing (`35-60` units), now that it's driving
  actual growth-cycle yield in the wheat-harvest plan, or is porting the
  same min/max size sufficient for a first version? Leaning toward porting
  as-is and tuning later alongside the yield constants already flagged as
  placeholders in the wheat-harvest plan.
- Should `generate_landarea.py`'s separate, centered-on-village
  grazing/mixed_crops `Subzone`s eventually be reconciled with this
  dedicated "Farmland" `LandArea` (e.g. merged into one coherent
  agricultural-land picture), or left as unrelated decorative data? Leaning
  toward leaving them alone - out of scope, no code currently reads them
  either.
